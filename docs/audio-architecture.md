# Windows 语音处理设计 · 2026-09-29

## 用户确定的方向

- 主要交付场景是 Windows EXE。
- 采用 Typefree 的边录边提交，以及语音处理和本地数据行为。
- ASR 与文字模型的服务地址、模型、密钥由用户自行配置。
- 保留此前明确要求的 vibevoice-windows 切换式快捷键、D 墨珠动效和 Windows 构建方式。

本文是设计与验收基线。以下进度按源码、自动检查与 Windows 实机三层分别记录；自动检查通过不等于 Windows EXE 已验收。

## 2026-09-29 实施进度

- Windows 正式路径已改为 Rust/CPAL 的 WASAPI 共享采集，后台下混、连续重采样、停顿分段、录音中串行识别与尾段收尾；前端只收电平和状态。浏览器预览改用 AudioWorklet。
- 原始音频按约 2 秒的增量块使用 Windows DPAPI 加密暂存。ASR 失败可重试；重启后可恢复录音。历史文本同样使用 DPAPI，先验证写入再迁移旧 localStorage；历史录音由用户选择保留，并随历史期限清理。
- 默认智能整理、短句本地直出并去掉末尾句号、最终词库纠正、普通口述文字失败回退、首尾翻译口令、文字候选路由、多轮流式问答、登录启动和取消链路已经进入源码。
- 用户选择通用 OpenAI 兼容 **WAV** 接口；因此本版本固定上传 16 kHz PCM16 WAV。未向未知服务发送 AAC/M4A 或私有词汇上下文参数，也未假定额外并发额度。
- Mac 上的 JS/Rust 测试与构建、Windows 音频/DPAPI/启动模块的独立目标类型检查可验证源码范围；完整 Windows EXE 构建、设备录音、UIA、服务联调、安装包与性能/准确率测量仍须在 Windows 执行。

## 1. 采集、内部表示、上传编码分别设计

| 层 | 职责 | 决定 |
| --- | --- | --- |
| 麦克风采集 | 与设备、系统权限、设备切换交互 | Rust 后端使用 WASAPI 共享模式；可通过 CPAL 封装 |
| 内部音频表示 | 分段、电平、重试、编码的共同输入 | 保留必要 PCM 样本；分段分析使用 16 kHz 单声道 Float32 |
| 上传编码 | 将完整音频段交给模型接口 | 当前固定为 16 kHz 单声道 PCM16 WAV，与用户选定的通用接口一致 |
| 前端 | 设置、快捷键反馈、HUD、结果 | 接收状态、电平与文本；正式桌面链路不经 JS 传输整段音频 |

原生采集不会自动提高识别准确率。选择它的主要依据是后台托盘运行、设备管理、音频与界面生命周期分离，以及减少大段音频在 JS/Rust 间复制。

### Windows 采集约束

1. 使用设备支持的原生/共享混音格式（常见 44.1/48 kHz），不强制设备提供 16 kHz。
2. 在独立音频线程接收数据；回调只做有界缓存入队，不执行 HTTP、磁盘 I/O 或阻塞编码。
3. 后台处理线程下混为单声道，并以保留滤波状态的重采样器生成 ASR/分段所需采样率；不能把每个回调块当作独立录音重采样。
4. 当前 Web Audio 请求回声消除、降噪。WASAPI 原生采集不自动等价于这些处理：需明确系统增强和应用 DSP 的责任，避免双重处理，并用安静/噪声场景对比后决定默认设置。
5. 支持默认麦克风和设备选择；设备拔出、权限拒绝、格式变化必须反馈状态，保留已录内容，不能无提示地产生缺口。
6. 录音会话 ID、样本位置、分段序号统一贯穿录音、识别和粘贴；取消必须进入后端，发送 Ctrl+V 前再次检查。
7. 缓冲有上限；长录音保留与恢复需使用受保护的本地暂存，不能无限积累 PCM 或每 2 秒复制从开始到现在的整段录音。
8. 音频处理持续在后端运行；向 HUD 发送约 30 Hz 的电平数据，具体节流与延迟通过测量调整。

浏览器预览若继续提供录音，应使用 AudioWorklet。它服务于预览，不作为 Windows 正式采集的隐式回退；原生采集失败必须显示原因。

## 2. 格式与体积

原版 M4AEncoder 使用 AAC、单声道、输入采样率、24 kbps；当前输入链路为 16 kHz。当前复刻版上传的是 16 kHz、单声道、16 位 PCM WAV。

| 编码 | 理论音频载荷/分钟 | 说明 |
| --- | --- | --- |
| 16 kHz PCM16 单声道 | 1.92 MB | 不含很小的 WAV 头；256 kbps，无有损压缩 |
| 原版 24 kbps AAC | 约 180 KB | 未计 M4A 容器，实际码率可能波动 |
| Windows 系统 AAC 的 96 kbps 配置 | 约 720 KB | 不能据此声称与原版一样缩小十倍 |

Microsoft Media Foundation AAC 编码器文档列出的输入采样率是 44.1/48 kHz，码率从 96 kbps 起。实现时应查询编码器能力，不能把 macOS 的 16 kHz/24 kbps 参数直接复制过去。

本版使用 WAV。若以后明确要求原版低码率压缩比，需要单独选择并随应用分发支持该参数的编码器，且验证服务接受格式、识别质量与构建产物。该选择不能靠更改文件扩展名或 MIME 类型完成。

### 与自定义服务配合

- 固定以 WAV 上传，不假设“OpenAI 兼容”就支持 AAC/M4A、私有词汇上下文或额外并发额度。
- 原 PCM 保留到本段识别成功，失败后可按原格式重试；格式被服务拒绝时明确提示用户，不擅自改动文件扩展名或 MIME。
- 每一段必须是独立、有效、已完成封装的文件；不上传未完成的 M4A 文件片段。
- `filename`、MIME、采样率和实际字节格式一致。

## 3. 对齐 Typefree 的提交时机

采用分段 HTTP 识别，不要求服务提供 WebSocket：

1. 录音时持续采集，约每 2 秒评估新增音频。
2. 使用相对能量低谷寻找停顿，沿用目标段长约 6 秒、最短提交约 3.5 秒、保留活跃边缘约 1.5 秒的初始参数。
3. 找到合适停顿才提交；不能按固定秒数强制切开正在说的词。
4. 录音中的提交默认串行，成功后推进已识别位置；失败或无内容时保留音频，供下一段合并或结束后重试。
5. 结束录音后等待在途段，处理尾段，按音频次序拼接，再走全文整理和最终词库纠正。
6. 无合适停顿时退回整段处理；当前接口没有并发额度依据，尾段与录音中分段串行提交。
7. 原始完整录音保留到结果确认；缺失片段不能静默表现为完整成功。恢复失败时保留录音与错误状态供重新转写。
8. 中间识别结果只用于内部缓存或状态展示；最终成稿确认后统一输入，避免反复修改目标应用文本。

预期减少的是“结束录音后的等待”；不是保证整体耗时更短。实际效果必须用同一批音频测量请求数、上传字节、末尾等待、词错率和完整率。

Windows 的历史保护使用系统保护能力或由凭据库保管密钥的加密存储，不能直接照搬 macOS Keychain API。旧历史迁移要先写新文件并校验，保留可恢复副本；导出则由用户显式触发。

“完全采用”在此指语音处理与本地数据行为的对齐；平台 API 采用 Windows 对应实现。此前已确定的快捷键、动效、构建方式与本次自定义模型要求是明确例外。

## 5. 实施与验收顺序

1. 先对齐可独立测试的文本处理行为、最终词库纠正与后端取消。
2. 建立 Rust 音频服务与 Windows WASAPI 采集，验证设备格式、取消释放、后台运行和真实电平。
3. 接入分段识别、尾段收尾、失败合并恢复；通过可控制的测试 ASR 验证乱序、限流、重试与取消。
4. 使用选定的 WAV 协议联调真实服务，确认 multipart 字段、模型名与响应格式。
5. 对齐加密历史、音频恢复、翻译、问答与桌面生命周期。
6. Windows 完整构建及实机验收后再声称完成；Mac 单元测试与类型检查不能替代这一步。

关键用例：短句不切段；长句有停顿可提前识别；连续说话无停顿不硬切；静音不会生成正文；最后一段失败不丢句；任意阶段取消不再投递；蓝牙/USB 麦克风断连可恢复已录内容；已学习术语经过文字模型后仍被保留；WAV 格式拒绝时明确提示；历史加密且可重启读取。
